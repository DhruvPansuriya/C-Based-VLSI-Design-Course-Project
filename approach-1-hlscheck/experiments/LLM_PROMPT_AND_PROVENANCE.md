# LLM optimization record

The candidates in `catalog.json` were generated by the Codex assistant while
working on the user's Project 3 request. They are not copied outputs of an
unrecorded benchmark run or calls to an external API. The exact API model ID,
temperature, tokens and response IDs were not exposed, so those fields are not
claimed. This is a single assistant-session case study, not a multi-model study.

## Optimization instruction used for this generation stage

Given each original `kernel` implementation, produce an HLS-oriented C rewrite
that preserves its signature, all final array contents and return value for
every uint32_t input. Use modulo-2^32 arithmetic, fixed bounds, and nonoverlapping
array parameters. Do not introduce new input restrictions, floating point,
dynamic memory, calls or narrower types. Consider loop restructuring, reuse of
partial results, symmetric FIR coefficients, separable box filtering, and
algebraic factoring. Keep interface and compiler settings fixed for comparisons.
Treat the rewrite as a candidate until the independent SMT checker verifies it.

## Source of original references

GEMM and stencil follow the downloaded MachSuite algorithms with explicit type
and dimension adaptations, described in `benchmarks/machsuite_u32/README.md`.
The remaining cases are small educational kernels, not claimed as untouched
standard-suite benchmarks. The unswitching case is adapted from the course.

The `*_original.c` and `*_optimized.c` files are the exact recorded source
artifacts. Experiment results record their SHA-256 hashes. Candidate generation
and acceptance are separate stages; actual QoR improvement is determined only
after synthesis, and unchanged or regressed cases remain in the results.

## Negative controls

The `*_buggy.c` files are deliberately seeded controls to validate rejection and
counterexample generation. They are not spontaneous LLM mistakes and must not
be used to estimate an LLM bug rate. The exact mutations are documented in each
file's leading comment. Proof failures are never silently reclassified.

## Expanded round on 22 November 2026

The user requested approximately 40-50 tested HLS designs with recorded source
optimizations and equivalence results. We chose 48 original/candidate pairs
(96 synthesized implementations) by adding forty educational pairs. This
unit of counting is explicit: the workload contains related min/max,
population-count, matrix and data-movement variants, and a second GEMM
candidate against the same original reference. There are 47 distinct original
C ASTs after comment/format removal, not 48 independent applications.

The generation constraints remain unchanged: same interface and dimensions,
all final outputs preserved, unsigned 32-bit modular arithmetic, valid disjoint
arrays, no extra input restrictions. Candidate techniques include independent
accumulators, comparison trees, loop fusion, bitwise permutations, SWAR byte
counts, running-window reuse, separable filtering, dynamic-programming reuse,
local GEMM accumulators and structural bound tightening.

`tools/expand_benchmarks.py` records the exact forty source definitions and
materializes standalone original/optimized/faulty C files. It is deterministic
source materialization, not a claim of a separately logged API inference run.
The before/after dossiers in `experiments/optimizations/` record every actual
source, rationale, hash, proof chain, witness and measured QoR result.

All forty additional faults are explicitly seeded output-bit flips. The first
eight controls retain their earlier structural/arithmetic mutations. This mix
demonstrates checker behavior and replay; it is not a diverse independent
mutation campaign or a spontaneous LLM failure dataset.

The initial Hamming monolithic proof attempt timed out and is retained under
`experiments/attempts/hamming8_monolithic/`. The final source pair is unchanged;
the checker was improved with independently discharged additive component
lemmas. Every accepted lemma and final query was replayed with Z3. The later
successful proof is not substituted for the retained initial unknown record.

## Feedback round: 50 pairs / 100 implementations

After the user asked to continue, two additional follow-ups reused existing
originals: moving_sum_register16 holds the window in scalar registers, and
gemm_tile2 tests two local output accumulators. They bring the final study to
50 pairs / 100 hardware implementations while the distinct-original AST count
remains 47. Source definitions are in `tools/add_feedback_candidates.py` and
standalone files in `benchmarks/feedback/`.

Both candidates are formally equivalent. GEMM's two-column tile measures 94
cycles against 122 and improves area x latency by 1.34%. The register-window
candidate has no cycle advantage over the earlier sliding recurrence and
increases area; it is rejected. Earlier candidates are preserved and linked
in the per-pair dossiers. The final cohort has 22 ADP improvements, 25 ADP
regressions and three unchanged cases under the documented 0.1% tolerance.

SAT query replay now checks the exact recorded input witness. Every UNSAT
main query and accepted component lemma still replays without those extra
constraints. Earlier unconstrained SAT-replay budget failures are retained
under `experiments/attempts/sat_replay_budget/`; they are not mislabeled as
proofs. Compiled-C witness replay remains separate from SMT replay.
